# 素材追加から公開まで

## 人間が用意するもの

- 詳細画面：名前・レアリティ・コスト・レベルが写った星1/2/3。
- Lvボーナス：最初から最後まで。隣の画像と1行程度重ねる。
- バリアント：星別詳細画面と、そのバリアントの育成一覧。
- 新しいキーワード：説明画面。
- 短い攻略メモ：評価、使い方、相性、注意点。画面にない撮影条件があれば補足。

スマートフォンの元ファイル名で構いません。撮影セット単位のフォルダ分けは任意です。1枚に複数キャラがいても問題ありません。今回の2体のアイコンは同じ原本から生成しています。

## Workに依頼する例

「今回追加したスクリーンショットを確認し、対象ミニオンと用途を分類してください。既存の公開データと記事を先に読み、画像で確認できた客観情報と攻略メモの差分だけ反映してください。原本の改名・変更は禁止。未確認を推測で埋めず、逆算は条件付きで保持してください。画像加工・検証・build・previewまで行い、公開・commit・pushはしないでください。」

## Workの作業

公開記事は人間が確認・編集した攻略情報として届ける。AI・画像認識などの制作方法や「追記確認」などの管理用ラベルは本文・性能表へ出さない。確認経路はデータと確認票に保持し、読者には未確認・逆算の前提・表示レベルなど判断に必要な情報を示す。

1. `npm run inventory` で素材を列挙。未登録画像は「未分類・確認待ち」として出力される。スクリプトは画像内容を推定しない。
2. 対象画像を目視し、`work/sources.yaml` に根拠ID→原本相対パス・分類状態を記録。複数IDが同じ原本を参照してよい。不確実な分類は `pending`。
3. `data/sources.yaml` に同じIDと説明を登録。ここにはローカル原本パスを入れない。
4. `data/minions/<id>.yaml` を差分更新。画像にない値は `unknown`。人間の追加確認値は `manual` と出典を記録。既存manual値を画像で勝手に上書きしない。矛盾は確認票へ追記。
5. `content/<id>.md` の該当箇所だけ編集。元メモの性能欄から初期値を補完しない。攻略メモを清書する場合も新しい攻略事実を創作しない。
   攻略評価・使い方は書き手自身の意見として記述する。「運営者のメモでは」「運営者の評価では」といった伝聞形式は使わず、「組み合わせが有用です」「早めの配置がおすすめです」などと書く。元の評価の意味・確度は維持し、未確認情報を断定しない。
6. 新画像が必要なら `data/assets.yaml` に公開パスとaltを登録。`work/recipes.yaml` に原本パス、分類結果、切り出し・マスク・サイズを記録。
7. `npm run images`。`work/processed/images/` の画像を開き、切れ・誤ったキャラ・名前やチャットの残存・文字潰れを確認。
8. 確認したレシピだけ `reviewed: true` にして `npm run images:publish`。これはローカルのpublicへの反映であり、インターネット公開ではない。
9. `npm run review`。根拠・未確認項目と公開画像をまとめた確認票ができる。
10. `npm test` と `npm run build`。未確認は警告情報として許容し、データ形式・参照・画像・リンクの不備はエラーで止める。
11. `npm run preview`。人間へ確認すべき事項とローカルURLを報告。

加工だけを1枚試す場合は `npm run images -- --only=mam-icon`。同じ指定は `images:publish` でも使える。

## 通常画面とランブルチェス画面の判別

読み取り前に画面全体を見てモードを判別し、根拠台帳にmode（standard / rumble-chess / unknown）とscreenを記録する。不確実ならwork/sources.yamlのstatusをpendingにする。

| ランブルチェスの特徴 | 扱い |
|---|---|
| 左上の絆表示・ステータス内の絆ポイント | モード判別の主な手掛かり |
| 星の選択タブが4まで | モード判別の主な手掛かり |
| 現在Lvと最低保証Lv.7が併記 | 保証未達の場合のみ。Lv.8などで併記がなくても通常画面とは判定しない |
| バリアント表示がない | この特徴だけでモードを決めない。不存在の根拠にも使わない |

通常詳細と判断でき、バリアント欄が出る領域を含めて画面が見えていて、表示がなければ「バリアントなし」とする。星3までで絆・絆ポイントがないことも確認する。切り抜き、説明ポップアップ、遮蔽がある画像では保留。data/sources.yamlにmode: standard、screen: detail、variantControl: absentを記録し、variants.sourcesから参照する。オーキッド占星術師はこの方法で確認済み。

絆はカードプール一覧の見出しとミニオン名からまとめて取得する。6デッキは雲・月・太陽・雷・雫・星。詳細画面のアイコンは概要画面のアイコンと照合する。色だけで決めない。見出しが欠ける場合は重複範囲のある画像で所属を確認し、不明なら保留する。一覧に見当たらないだけで所属なしとはしない。

取得結果はdata/rumble-chess.yamlを正本として保存し、現在のサイト表示には使わない。通常詳細から取得する性能は従来どおりdata/minionsへ保存する。ランブルチェス詳細の表示数値を通常性能や初期値の補完に転用しない。現在Lv・最低保証Lvは別に保存する。

ランブルチェス画像は任意。絆を一覧から確認できればミニオンごとの詳細撮影は不要。星4画像も必須にせず、規則性があるという情報だけで数値を推定・確定しない。将来計算が必要になったときに対象と式を確認し、derivedとして扱う。

## 加工レシピの形式

```yaml
- asset: example-icon
  source: 撮影セット/Screenshot_001.png
  classification: confirmed
  reviewed: false
  expectedSize: [1080, 2340]
  crop: { left: 100, top: 300, width: 400, height: 400 }
  masks:
    - { left: 110, top: 320, width: 100, height: 30 }
  width: 160
  quality: 90
```

座標はすべて**原本のピクセル座標**。マスクは不透明黒で画素を置き換え、その画像をトリミング・縮小・WebP化する。メタデータは引き継がない。原本サイズ違い・範囲外座標・フォルダ外への入出力はエラー。

`classification: pending` は処理を保留する。`reviewed: false` では公開用への反映を止める。原本・レシピを変えたら必ず false に戻して再確認する。高度な変更検知は未実装なので、同じ名前の原本を上書きせず、別ファイルとして追加する。

公開用画像は派生物なので再生成可能。記事とミニオンデータは正本であり、画像スクリプトから書き換えない。公開用画像を追加・削除したら assets 台帳と参照も同時に更新する。使われなくなった画像の自動削除は行わない。

## 新しいミニオンを1体追加する具体的な手順

1. ユーザー：raw-screenshotsへ必要画像、article-notesへ攻略メモを置く。
2. Work：固定IDを決め、画像を見て分類。既存ミニオンの重複登録でないことを確認。
3. Work：data/minionsの既存1体を**形式の参考**にし、新規YAMLを作る。数値・出典・評価を他キャラから流用しない。未知項目は理由つきunknown。
4. Work：最低レベルはレア1・エピック4・レジェンド7を使う。星別の撮影条件が異なる場合は同じ表にまとめず、揃った素材を待つか未確認で残す。
5. Work：基本形のbonusesとバリアントごとのbonusesを個別に入力。全Lvが読めなくても欠落行をunknownとして保持できる。
6. Work：新規Markdownに minionId を指定。性能表は本文に手書きしない。
7. Work：アイコン・立ち絵を生成し、images:publishでローカル反映。
8. Work：review・test・build・preview。新ミニオンは一覧・詳細ルートへ自動追加される。ページコードの追加は不要。
9. ユーザー：数値、未確認の扱い、攻略文、加工後画像、スマホ表示を確認。
10. 公開指示後にGitHubへの反映とPagesの手動公開を行う。

## バックアップと公開範囲

work/ は非公開だが、原本と加工設定・分類台帳は再加工に必要。原本・メモと一緒にバックアップする。別PCで公開用リポジトリだけ取得してもbuildできるが、再加工には別途この非公開素材が必要。

今回未採用のアッポリス・マッスルスイカの素材はそのまま残している。inventoryの未分類表示は消さず、次回の処理対象として利用する。
