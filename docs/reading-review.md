# 画像からのデータ登録と再読確認

対象はミニオン、運命のギフト、バッジ、絆、用語など、画像から読む客観情報全般。読み取りと登録の確認はWorkが実施し、人間には不一致・判読困難・保留事項を優先して報告する。人間の全件確認を前提にしない。自動OCR・外部AI APIは追加しない。

## 1. 編集前に対象を決める

全画面を開いて対象と画面種別を分類する。ファイル名や他の画像の傾向から分類しない。分類不確実ならwork/sources.yamlをpendingにして保留。

今回の対象・画像根拠ID・読む項目をwork/registration/の作業メモに列挙する。各項目を「確認する」「資料不足でunknown」「対象外と理由」のいずれかに割り当て、空欄を残さない。

| 画面 | 読取前に確認する項目 |
|---|---|
| ミニオン詳細 | 名前、基本形／バリアント、通常／ランブルチェス、現在Lv、保証Lv、選択中の星、レアリティ、コスト、攻撃力、攻撃間隔、対象、能力全文、入手・カードプール解放条件、バリアント表示領域 |
| 育成・Lvボーナス | 対象と形態、育成Lv、各行のLv・効果全文、先頭と末尾、重複と欠落。詳細画面のLvと分離 |
| 運命のギフト | 名前、ラウンドの画像根拠またはユーザー指定、効果全文、下部の解放条件、アイコン |
| バッジ・チャーム・用語 | 名前、種類、段階、効果全文、数値・単位・発動条件、解放条件の有無を確認できる画面か、アイコン |
| カードプール・絆 | 見出し、対象名、所属、段階値、効果全文、画面の端・続き。未掲載から非登場を推測しない |

既存のモデルに保存先がない項目も作業メモに残し、保存先を検討する。見つけた情報を黙って捨てない。公開データの未知項目はunknownと理由を使う。

初回導入時だけ `npm run registration:init` で現在のデータを変更検知の開始点として保存する。これは既存値の正しさの認定ではない。基準が存在する場合は再初期化しない。作業開始後に初期化すると変更を検出できないため、必ず編集前に行う。非公開素材のない新環境では基準と確認記録も復元する。

## 2. 初回読取と別工程の再読

1. 全画面で条件を確認した後、名前・数値・能力・解放条件などを項目別に拡大して読む。固定座標は画面ごとに妥当性を確認し、文字の途中・画面下端で切れていないかを見る。
2. 初回値をwork/registration/checks.yamlのfirstに保存する。数字だけでなく、単位、対象、タイミング、一時的／永続的、否定、括弧内の変動値も読む。
3. 初回値・登録値を参照せずに原本から再読し、secondに保存してから照合する。同じ値のコピーや言い換えを再読扱いにしない。同じ読み手なので誤りが相関する限界はある。
4. 一致したら既存の正本を差分更新し、registeredに登録項目全体を記録する。違えば全画面と拡大画像に戻り、解消できなければunknown・保留とする。修正前の不一致は作業メモに残す。

「表示なし」は未読の初期値にしない。該当欄が出る画面とその全領域を確認でき、文字・表示がない場合だけabsent。切れ・遮蔽・別モードはunknown。absentは全件再読する。通常画面のバリアント不存在など、既存の個別ルールも満たす。

数値・条件を含め、変更した全項目を再確認する。件数やラウンド別傾向は異常発見の補助であり、自動補完・自動訂正には使わない。

## 3. 確認記録と画像を並べて照合する

キーは `data/ファイル.yaml#/項目/配列番号/項目`（JSON Pointer、配列番号は0始まり）。statusを持つ項目は項目全体が1単位。それ以外の名前・星・Lv等も値ごとに対象になる。id・updated・schemaVersion、画像台帳・根拠台帳はこの差分検査から除外し、従来の検証と分類・画像確認で扱う。

形式例（値・根拠・座標・ハッシュは実際に確認した内容を記録する）:

```yaml
data/fate-gifts/example.yaml#/unlock:
  registered:
    status: observed
    value: トロフィー数550個で解放
    sources: [example-detail]
  first: { status: observed, value: トロフィー数550個で解放 }
  second: { status: observed, value: トロフィー数550個で解放 }
  context: 対象名、ラウンド10。ラウンドは今回のユーザー指定と照合
  evidence:
    - source: example-detail
      sha256: 原本のSHA256を小文字で記録
      region: { left: 0, top: 1800, width: 1080, height: 200 }
```

- registeredはsources・note等も含む現在の項目全体。first/secondは通常 `{status, value}`、absentは `{status: absent}`、通常の文字列や数値はその値。valueを持たない複合項目は全体を記録する。
- absentでは `fullRegionVisible: true` が必須。これは実際に領域全体を見た後だけ記録する。
- unknownではregisteredと `holdReason` を記録し、無理に再読一致を作らない。保留は完了報告にも残す。
- manualはユーザー確認の出典、derivedは式・前提・入力値を照合し `basis` に記録。画像確認値へ置換しない。
- statusを持たない評価・管理値等は、元メモ・ユーザー指示などとの二度の照合とbasisで記録できる。画像から読む名前・数値にはevidenceを使用する。
- 削除はregisteredを省略し `deletionReason` を記録する。
- 原本ハッシュは `Get-FileHash -Algorithm SHA256` 等で取得する。原本パスは公開データに保存しない。

`npm run registration:check` は変更項目の未記録、初回・再読・登録値の不一致、確認後の値変更、未分類根拠、原本の変更、範囲外の切り抜きをエラーにする。work/registration/review.htmlには登録値・二つの読取値と根拠の切り抜きを並べる。原寸画像も開けるので小さい文字は拡大して確認する。確認用切り抜きは非公開で、公開アイコンを生成するimages処理とは別用途。

照合票を実際に開き、画像と登録値・条件を確認する。全画面での対象確認を切り抜きだけで代用しない。位置を間違えた切り抜きや、読取値のコピーはプログラムで見破れない。保存されていない項目の読み落としも差分検査では拾えないため、最初の項目一覧と最後に突き合わせる。

## 4. 登録を完了する

1. 最初の項目一覧を照合し、確認済み・unknown・対象外の理由がすべて揃っているか確認。
2. 画像追加時は従来どおりimages → 加工画像の目視 → reviewed → images:publish。
3. `npm run review`（読取照合も実行）、`npm test`、`npm run build`。形式検査・build成功を読取の正しさの保証としない。
4. 照合票の目視後、`npm run registration:accept`。再検査が通った場合のみ旧基準と記録を保存し、次回の変更検知の開始点を更新する。
5. 対象件数・確認した範囲・修正・未解決事項を報告。既存データ全体を再確認したとは報告しない。

通常buildは非公開台帳を要求しない。登録作業の完了判定にはreviewが必要。公開用リポジトリだけでのbuildと、原本を使った登録確認は別の検査である。

既存値は今回の導入では再監査していない。今後の再監査はabsent、数値・解放条件、形態・モード・Lv混在の疑いを優先する。未変更の既存値を検査する場合も同じ読取手順と照合記録を残し、修正した項目は差分検査を通す。
